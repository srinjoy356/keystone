3 · Remember

It remembers, and remembering changes its answers.

Memory here is not a chat log. Each person gets their own FalkorDB graph holding what they asked (episodic), what they approved or rejected (semantic) and rules they taught it (procedural). Try it: three steps, all real.

4 · Act

Agents that hand off work, and take real action.

A triage agent queues open pull requests and notes which touch at-risk modules. Router workers claim tasks through one atomic write, so two workers can never take the same one. When you approve, an executor opens a real issue in our sandbox repository. It never writes to the project being analysed.

The shared queue

Tasks live as nodes in a FalkorDB graph that every agent reads and writes.

5 · Trust

Does it actually work? We measured it.

We hid the real reviewers of later pull requests and asked each method to predict them using only the history before each PR was opened. Weights were tuned on separate data; the test slice was never touched.

93%of the time a real reviewer is in Keystone's top three

The model is never trusted on its own

An LLM proposes decisions with a quote. Code keeps one only if the quote is a verbatim substring of the source message and a second check confirms it states the decision.

What we do not claim

  • It predicts who did review, a proxy for who should.
  • Risk is per module, never a judgment of a person; only public handles are used.
  • The docs repository is the weak case (0.65): its main reviewer changed over time.
  • We have not measured time saved for a real team.

6 · How it works

A graph, nine fixed tools, and an agent that cannot touch the database.

Everything the product knows lives in FalkorDB. Take FalkorDB away and there is nothing left to run.

1 FetchPublic PRs, reviews and issues from GitHubgithub.py
2 LoadIdempotent MERGE into a graph per tenantload.py
3 DerivePageRank, betweenness, label propagationderive.py
4 VerifyLLM proposes decisions, code checks the quotedecisions.py
5 QueryNine fixed read-only tools, parameterised Cyphertools.py
6 AgentPicks tools, explains results, shows evidenceagent.py

The graph model

PersonPRIssueModuleFileDecision
(Person)-[:AUTHORED|REVIEWED]->(PR)-[:TOUCHES]->(File)-[:IN]->(Module)-[:PARENT]->(Module)
(Decision)-[:DECIDED_IN]->(PR|Issue)      (Person)-[:STATED]->(Decision)
(Person)-[:COLLAB|LINKS|KNOWS]-> derived for algorithms and paths
one graph per tenant (kb_x), per user (mem_x), per task queue (ops_x)

FalkorDB features used: openCypher, variable-length traversal, PageRank, betweenness, label propagation, shortest path, HNSW vector index, named graphs, RO_QUERY.

The query behind "who should review this?"

MATCH (f:File) WHERE f.id IN $files
MATCH (p:Person)-[r:AUTHORED|REVIEWED]->(pr:PR)-[:TOUCHES]->(f)
WHERE pr.createdAt < $asof AND p.login <> $author
RETURN p.login,
  sum( (CASE type(r) WHEN 'REVIEWED' THEN 1.0 ELSE 0.5 END)
       * exp(-($asof - pr.createdAt) / $tau) ) AS s

History strictly before the PR, reviews weighted above authorship, exponential recency decay (tau 90 days). The same query, with $asof set to each PR's creation time, is the evaluation.
